# Incremental ROS pathing and two-thruster control

## Runtime data flow

USV-only: teammate color model + rectified USV camera + capture-time camera/LiDAR
TF -> /perception/buoys/usv -> tracker -> /mission/buoys -> incremental planner.
Duo: calibrated UAV camera detections/pose -> /perception/buoys/uav -> Jetson
tracker and incremental planner, with local LiDAR geometry retained for precision.
Both feed the same local trajectory protocol and professor controller on Jetson.

The planner keeps the learned map and mission progress in its process RAM. It
can move with a partial map, obtain new views, and replan without erasing completed
entry/passages. Neither mode requires all buoy labels. Advanced entry/exit and
successful-report requirements remain explicit. The browser's simulated report
acknowledgement is never generated by the real ROS adapter. Use the actual OCS
integration to signal /mission/task1/survey_reported after successful reporting.

The real UAV geometry adapter uses actual camera calibration and capture-time TF;
it is not the USV's forward camera model. The v4.1 simulator's automatic descent
is NOT installed as a real UAV flight policy by this package. Existing UAV flight
and color-model processes remain separate. No UAV arming/takeoff is requested.

## Interfaces

| Topic/service | Producer -> consumer | Contract |
| --- | --- | --- |
| /mission/buoys | tracker -> incremental planner | Shared frame/datum, captured evidence and conflicts |
| /usv/coordination/odometry | localization -> planner/controller | Shared ENU pose; actual capture times; topic is configurable |
| /scan | LiDAR -> planner | Capture-time TF; fresh swept-hull/braking-horizon coverage |
| /mission/trajectory_preview | planner -> controller | Three samples at t, t+dt, t+2dt; C2 pose/rates/accelerations; run/datum IDs and validity |
| /control/thruster_forces | controller -> optional force bridge | Typed Ft3 right/Ft4 left, source timestamp/expiry, run/controller IDs, sequence, validity and confirmed-contract flag |
| /control/professor_status | controller -> logs | Errors, limits, force rates, derivative mode, force requests |
| /vehicle/professor_actuation_status | force bridge -> logs | Calibrated normalized motor/mixer requests and optional measured RPM/torque/PWM/voltage estimates |
| /mission/task1/start, stop, reset | operator -> planner | Trigger services; resetting clears learned map/progress |
| /vehicle/software_estop, set_autonomy | operator -> force bridge | Existing SetBool authority services; startup stopped/disabled |

No force is published as cmd_vel or interpreted as a speed. C2 quintic Hermite
interpolation aligns preview samples to measured state, allowing only the explicit
capture-sync tolerance; it never predicts future actual vessel state. Invalid,
stale, wrong-frame, wrong-datum, HOLD or terminal references produce invalid zero
force requests and reset accumulated correction. Force-command expiry is bounded
by the pose/reference validity deadlines and two control periods, so the bridge
cannot continue using a force after its supporting reference expires. A source/controller restart
requires renewed authority if the hardware force backend was active.

The real clearance monitor checks the reference corridor. It is not a validated
force-driven vessel dynamics predictor. Actual disturbances, localization noise,
tracking excursions and stopping behavior require closed-loop hardware validation.

## Calibrated force backend

The existing boat_vehicle bridge is refactored with one output hook. Its ordinary
velocity behavior is unchanged; all authority, operator, software-stop, mode and
command-timeout methods remain intact. The optional ProfessorForceBridge inherits
those checks and replaces only autonomous output and force-specific validation.
Operator Twist handling still goes through the original manual takeover path.

The force backend operates in explicitly observed Rover MANUAL mode, using the
project's existing validated MANUAL_CONTROL mapping: y steering, z throttle,
x=r=0; neutral y=z=0. This avoids placing an extra ArduRover velocity PID underneath
the professor's force requests. It does not automatically arm, change SERVOx
settings or switch into MANUAL. Stop behavior still requests HOLD.

A measured per-thruster force->normalized motor-command curve compensates for
motor differences. A separately verified FCU mixing matrix is inverted to obtain
manual throttle/steering. No mixer/channel/sign or cubic thrust/voltage law is
inferred. A singular matrix, out-of-range force, invalid calibration voltage,
stale battery/state/force data, or unconfirmed model contract withholds output.
Battery policy is enforced for this new backend; the old backend is not changed.

The calibration template intentionally contains no usable synthetic thrust values.
Populate reverse, neutral and forward data, sorted by increasing vessel-forward
force and normalized command, for each motor at the actual battery voltage range.
The command definition includes the actual FCU mixer, reversals and ESC endpoints.
Record/verify these settings with the calibration; changed settings invalidate it.
Optional measured columns rpm, shaft_torque_nm, pwm_us and measured_motor_voltage_v
are interpolated if supplied. Missing quantities remain absent. The ESC command
is not a direct DC-voltage command; supplying battery voltage alone cannot determine
shaft RPM, torque or motor voltage under load.

Do not run the ordinary bridge and force bridge simultaneously. The package does
not modify boot services or select an active hardware controller automatically.
The launch defaults to planner + force computation only, start_force_bridge=false.
The hardware flag applies to autonomous force output; inherited human operator
control retains its existing independent authority behavior if the bridge runs.
